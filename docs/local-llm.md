# 自建 AI：在 2核2G 服务器上跑本地模型的可行性方案

> 结论先说：**能跑，但只适合当备用通道，不适合当主力。**
> 主力继续用免费的 GLM-4.7-Flash（1-2 秒出话），本地模型接成「云端挂了自动顶上」的兜底。
> 这套双通道已经写进后台，切换只需要在页面上点两下。

---

## 一、先把硬件账算清楚

你的实例是 `ecs.e-c1m1.large`：**2 vCPU / 2 GiB / 40 GiB 系统盘 / 无 GPU**。

CPU 推理时，模型权重必须整份装进内存。2 GiB 要减掉这些固定开销：

| 项目 | 占用 |
|---|---|
| Ubuntu 系统本身 | 200–300 MB |
| 宝塔 + nginx + php-fpm | 200–300 MB |
| MySQL（如果装了） | 300–400 MB |
| **留给模型的余量** | **约 1.0–1.3 GB** |

也就是说：**能跑 1.7B 的 4bit 量化，跑不了 4B 及以上**。这是物理上限，调参救不回来。

磁盘这边没问题：模型最大 1 GB，加上 llama.cpp 编译产物 1–2 GB，40 G 够用。

## 二、模型怎么选（都是 Apache-2.0，商用免费）

| 模型 | 量化 | 文件 | 运行时内存 | 2 核生成速度 | 判断 |
|---|---|---|---|---|---|
| Qwen3-0.6B | Q4_K_M | 378 MB | ~500 MB | 15–25 字/秒 | **稳，推荐先用这个** |
| Qwen3-1.7B | Q4_K_M | 1056 MB | ~1.35 GB | 6–10 字/秒 | 勉强，必须开 swap |
| Qwen3-4B | Q4_K_M | ~2.5 GB | ~3 GB | — | 2G 内存跑不了 |
| Qwen2.5-1.5B-Instruct | Q4_K_M | ~1.0 GB | ~1.3 GB | 7–11 字/秒 | 备选，中文略弱于 Qwen3 |

为什么是 Qwen3 系：中文原生、32K 上下文、Apache-2.0 可商用、GGUF 量化齐全（魔搭上 `unsloth` 镜像能直接断点续传下载）。

**为什么不用 Ollama**：它自带一层 runtime 和常驻守护进程，空载就吃 300–500 MB。2 GiB 的机器上这 500 MB 很致命。`llama.cpp` 是单个二进制，要多少内存给多少。

**为什么不用 vLLM / SGLang**：需要 GPU，直接排除。

## 三、三条路线，按推荐度排序

### ✅ 方案 A：云端为主 + 本地兜底（推荐，已实现）

```
访客提问 → 本地检索站内 699 条选题（0 成本）
        → GLM-4.7-Flash 组织语言（免费，1-2 秒）
        → 失败/超时/限流？自动改走本地 Qwen3
```

- 访客体验：和现在一样快
- 云端额度用完、网络抽风、Key 失效时，网站不会哑掉
- 额外成本：0 元（模型 1 GB 磁盘 + 500 MB 内存）
- **这是 2核2G 上的最优解**

### ⚠️ 方案 B：全本地（可行但体验会掉）

把主通道直接指向 `http://127.0.0.1:8080/v1`。

- 好处：完全不依赖外部、数据不出服务器、没有任何额度限制
- 代价：
  - 0.6B 回答偏「笨」，组织长句子容易跑题，只适合「挑题目 / 找选题」这类结构化任务
  - 1.7B 质量够用，但一条回答要等 **30–50 秒**，网页上访客基本等不住
  - 2 核只能同时处理 1 个请求（`--parallel 1`），第二个人来要排队
- 建议：只在你确定「访客少 + 更看重数据不外传」时选它

### 💰 方案 C：升级到 4核8G，跑 Qwen3-4B

- Qwen3-4B Q4_K_M 约 2.5 GB，8 G 内存能舒服地放下
- 生成速度 6–10 字/秒，质量接近早期 GPT-3.5，做站内问答够看
- 经济型 e 实例 4C8G 大约 100–200 元/月
- 只有「想把 AI 完全握在自己手里」才值得花这笔钱

> 补充一句：GLM-4-Flash / GLM-4.7-Flash 目前是**免费**的，且响应速度是本地 1.7B 的 20 倍以上。
> 纯从「省钱」和「体验」两个角度看，纯自建都不划算；自建的价值在**可控性和兜底能力**。

## 四、部署（三条命令）

在服务器上执行，全程约 10–15 分钟（编译占大头）：

```bash
# 1. 把脚本传上去（或者直接在服务器上新建后粘贴）
mkdir -p /root/llm && cd /root/llm
# 从仓库下载：deploy/local-llm/setup.sh

# 2. 跑（默认 Qwen3-0.6B，最稳）
sudo bash setup.sh

# 想要质量好一点、可以接受慢一些：
sudo bash setup.sh 1.7b
```

脚本会自动做完这些事：

1. 体检内存，不足时警告
2. **创建 2 GB swap**（关键，不加会被 OOM 杀掉）
3. 装 `cmake`/`g++`，浅克隆 llama.cpp 并编译 `llama-server`（`-DGGML_NATIVE=ON`，吃满 CPU 指令集）
4. 从魔搭下载 Qwen3 GGUF（378 MB / 1056 MB，支持断点续传）
5. 生成 32 位随机 API Key，存到 `/opt/local-llm/api-key.txt`
6. 写 systemd 服务：**只监听 `127.0.0.1:8080`**，外网扫描不到
7. 加内存熔断：`MemoryMax=1600M` + `OOMScoreAdjust=500`，真被挤爆时**优先杀模型，不连累 nginx/php**
8. 启动并做一次真实问答自检

跑完会打印三行接入参数：接口地址、模型名、API Key。

### 关于安全

- 只绑 `127.0.0.1`，公网无法直连，不需要开安全组端口
- 后端 `api.php` 的地址白名单只允许 `http://127.0.0.1` 和内网段走 http，公网地址必须 https
- API Key 落在 `/opt/local-llm/api-key.txt`（600 权限），网站侧存在 `data/ai-config.php`（`.php` 形式，浏览器直接访问返回空）

## 五、接到网站上

后台 → **AI 助手**，有两块：

### 主通道（现在用的）

保持不动：`https://open.bigmodel.cn/api/paas/v4` + `glm-4.7-flash` + 你的智谱 Key。

### 备用通道（新加的）

| 字段 | 值 |
|---|---|
| 启用备用通道 | 打勾 |
| 备用地址 | `http://127.0.0.1:8080/v1` |
| 备用模型 | `qwen3-0.6b` 或 `qwen3-1.7b` |
| 备用 Key | 粘贴 `/opt/local-llm/api-key.txt` 里那串（脚本没生成就留空） |

点「测试备用通道」→ 通了会显示模型名和耗时 → 保存。

### 想全本地怎么办

主通道那块点「一键填入本地模型」，地址变成 `http://127.0.0.1:8080/v1`、模型变 `qwen3-1.7b`，Key 留空，保存即可。访客端不用改任何东西。

### 一个自动处理的坑

Qwen3 系默认会先输出一段 ` thinking...` 思考链，900 token 的额度能被它吃光，用户最后只看到一个省略号。
后端已经在走备用通道时自动注入 `/no_think`，并清掉残留标签 —— 这个不用你管。

## 六、日常运维

```bash
journalctl -u local-llm -f        # 实时日志
systemctl restart local-llm       # 重启
systemctl stop local-llm          # 停掉（不用就停，立刻还 500MB 内存）
free -h                           # 看内存和 swap 用量
curl -s localhost:8080/health     # 健康检查
```

**换模型**（不用重新编译）：

```bash
sudo bash setup.sh 1.7b --no-build
```

**不想要了**：

```bash
systemctl disable --now local-llm
rm -rf /opt/local-llm /etc/systemd/system/local-llm.service
```

## 七、实测预期（别抱不切实际的期待）

用同一批站内问题对比（「我只有 STM32，两周能做什么」这类）：

| | GLM-4.7-Flash | Qwen3-1.7B（本地） | Qwen3-0.6B（本地） |
|---|---|---|---|
| 首字延迟 | 0.5–1 秒 | 3–6 秒 | 1–2 秒 |
| 完整回答 | 1–2 秒 | 30–50 秒 | 10–20 秒 |
| 引用编号准确率 | 高 | 中 | 低（经常漏 [1]） |
| 中文通顺度 | 高 | 中 | 偏低 |
| 并发 | 云端弹性 | 1 个 | 1 个 |
| 费用 | 免费 | 0 | 0 |

结论：**本地模型能「接得上话」，但接不住「体验」。**
所以把它放备用通道，是这台机器上唯一合理的用法。

## 八、什么时候该升级配置

出现下面任一情况，就该考虑 4C8G 了：

- 每天 AI 提问超过 200 次，且想全走本地
- 访客反馈「等太久」
- 想跑 4B 以上的模型（质量分水岭）
- 服务器同时跑 MySQL + Redis + 定时任务，内存常年 > 80%

在那之前，2核2G + 免费云端 + 本地兜底，是性价比最高的组合。
